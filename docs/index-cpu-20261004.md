# 索引服务 CPU 排查（2026-10-04）

用户授权本机测试。仅处理后台占用，未修改界面。

## 本机证据

- 6 个逻辑处理器。首次 46 秒 WMI 差分采样中，安装版索引服务整机 CPU 为 4.10%～5.03%，主程序为 0.14%～0.24%，网络代理为 0.10%～0.49%。
- Windows CPU 采样及带符号诊断版本调用栈确认两条主要路径：`ClientThread → HandleChanges → ChangeTracker::Summaries` 与 `Engine::FolderSizes → FolderSizeIndex::Build`。调用栈报告包含多种事件，未把其 inclusive hits 百分比当成 CPU 占比。
- 安装版阶段诊断的约 62 秒窗口内，没有 merge/rebuild；journal CPU 增量仅 62.5 ms。变更历史记录数为 100,000。
- 临时探针发现大小汇总反复失败：约 272 万节点中有 2,032 条存活记录指向非目录父节点。一次 45 秒窗口尝试汇总 18 次，每次约 0.3 秒。这是索引关系异常，不代表真实文件系统损坏。
- 短暂停服取得一致快照后恢复服务。两个持久化快照分别为 2,710,672 和 2,713,043 个节点，都包含同样的 2,032 条异常关系、154 个异常父节点；这些异常节点没有可供物理文件比对的卷 FRN 映射。

## 确定性复现与根因修复

旧版 v1 增量日志保存父节点编号，但不保存新增节点自己的全局编号。运行时不同磁盘交错新增，重启时却按卷分别回放，重新分配出的编号与原编号不同。

最小复现：C/D 根节点为 0/1，依次添加 D 目录（2）、C 文件（3）、D 子文件（4，父节点 2）。旧实现先回放 C 后，C 文件成为 2，D 目录成为 3，而 D 子文件仍指向 2，因此把另一个磁盘的普通文件当成父目录。旧实现的实际复现记录保存在 `build/multivol_replay_probe.log`。

- v2 日志保存新增节点原始编号，收集所有卷新增记录后按全局编号恢复，再应用各卷修改、删除及游标。
- 拒绝缺失/重复编号、截断记录和跨卷错误引用。v1 缺失的信息不能可靠补回，加载失败后丢弃内存中的部分结果，走已有重建流程。
- 缓存加载、写入及日志回放完成后检查父节点类型、范围、删除状态和环，异常关系不能继续固化或对外使用。
- 新快照发布后替换不兼容日志；NTFS 和 walk 模式均验证恢复后不会因旧日志循环重建。

已证实旧日志可确定性产生同类异常；没有历史执行记录能证明本机全部 2,032 条异常都来自这一处，不作该归因。处理已有异常依靠读取当前磁盘重新建立索引，不猜测或修补旧父节点编号。

## 修复

- 卷可见性未变化时保留查询缓存。
- 汇总失败后 30 秒内不重扫整棵索引，继续返回大小未知；快照替换立即解除等待，普通增量变化最迟在下次重试重新计算。
- 变更摘要的重命名事件只规范化新旧路径各一次，避免对每个祖先复制事件及重复规范化。保留身份去重、事件优先级与保留期语义。

## 验证

- 构建 `pulse_index`、`pulse_index_engine_test` 和 `pulse_change_tracking_memory_test` 成功。
- `--folder-sizes-only` 28 项通过，包含异常元数据、100 次失败后轮询不重算、重试到期、快照替换恢复正确大小。
- `--visibility-cache-only` 7 项通过；旧实现的对应检查曾有 2 项失败。
- 变更摘要 `--check` 通过，含 160 个滚动窗口、200 种路径/目录组合和 4,096 次迁移与旧算法对照。
- 最终构建 `pulse_index`、`pulse_index_engine_test`、`pulse_index_delta_replay_test` 成功。定向复验共 109 项通过：父链 12、大小汇总 28、可见性缓存 7、WAL 回放 62。没有运行完整历史回归。
- 新增定向检查已接入发布 CI；本次未执行发布流程。
- 隔离 100,000 条历史、25% 重命名、12 次重算对照：线程 CPU 从 4,734 ms 降至 1,813 ms。普通修改事件没有相应算法收益；不将该比例推广至所有工作负载。

上述 CPU 对照针对第一阶段减少重复计算的版本，不能当作最终 WAL 修复并重建后的服务 CPU 测量。
